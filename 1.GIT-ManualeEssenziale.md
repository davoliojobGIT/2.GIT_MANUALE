# GIT - Manuale Essenziale

## Cos'è GIT

Git è un programma che lavora su file di testo formattati e che consente di tenere traccia di tutte le
 modifiche apportate ai file nel tempo, permettendo di confrontare versioni differenti, 
recuperare versioni precedenti e collaborare con altre persone sullo stesso progetto e sugli stessi file, 
senza rischiare di sovrascrivere il lavoro degli altri.

E' studiato specificatamente per agevolare il lavoro in team di sviluppo sofwtare ma può essere utilizzato 
anche in altri ambiti dove vi sia necessità di collaborare su uno stesso progetto e/o file.

I file gestiti da GIT hanno spesso estensione ".md" **Markdown**.  
In realtà GIT non è limitato ai file .md: può gestire qualsiasi tipo di file, ma dà il massimo con i file di testo (Markdown, codice sorgente, configurazioni) perché può tracciarne accuratamente le modifiche riga per riga.

E' anche visto come un sistema di controllo di versione che permette di:

- salvare lo storico delle modifiche
- collaborare con altri sviluppatori
- tornare a versioni precedenti del progetto

# Le 3 Zone di Git

```text
Working Directory
       ↓
Staging Area
       ↓
Repository
```

## Working Directory

Contiene i file che stai modificando.

## Staging Area

Dove vengono spostati i file elegibili per essere salvati nel prossimo commit, cioè la successiva 
versione del progetto.

## Repository

Contiente tutti i file "committati", cioè lo storico delle versioni rese definitive del progetto.


### Utilità della Staging Area

La staging area esiste perché Git permette di decidere esattamente quali modifiche includere nel 
succesivo commit, invece di salvare automaticamente tutto ciò che è stato modificato come versione definitiva.

Nella staging area è possibile spostare dei file ma anche riportarli successivamente nella Working 
Directory. Questo permette di rendere definitive le modifiche importanti e ritenute corrette.

Ogni operazione di commit è associata ad un commento, utile per poter associare in modo più chiaro la versione 
alle modifiche in essa contenute e pertanto facilitare anche l'eventuale ritorno a versioni precedenti.

Infine permette di ragruppare in uno specifo commit delle modifiche al progetto coerenti con il nome/commento 
associato.

# Iniziare un Progetto con Git

Esistono due modalità principali per inizializzare un repository Git.

---

# Modalità 1 - Partire da un Progetto Locale

Utilizzare questa modalità quando il progetto esiste già sul proprio PC o lo si vuole creare in locale e successivamente  
ed eventualmente, pubblicare anche su GitHub.

## Lanciare Git per Windows

```bash
Se hai installato Git for Windows, nel menu Start dovresti trovare Git Bash.
Aprilo e usa Git direttamente.
```

## Creare la cartella del progetto

```bash
mkdir mio-progetto
cd mio-progetto
```

## Inizializzare Git

```bash
git init
```

Viene creata la cartella:

```text
.git
```

che contiene il database Git.

## Creare o copiare i file del progetto

Esempio:

```bash
echo "# Mio Progetto" > README.md
```

## Verificare lo stato

```bash
git status
```

## Aggiungere i file

```bash
git add .
```

## Creare il primo commit

```bash
git commit -m "Commit iniziale"
```

## Creare il repository su GitHub

Da GitHub:

```text
Accedere a GitHub
New Repository
```

Creare il repository senza aggiungere:

- README
- .gitignore
- LICENCE

per evitare conflitti con il repository locale.

Supponiamo che GitHub fornisca questo URL:

```text
https://github.com/utente/mio-progetto.git
```

## Collegare GitHub al repository locale

Dal prompt linux nella working directory digitare:
```bash
git remote add origin https://github.com/utente/mio-progetto.git
```

Verifica:

```bash
git remote -v
```

## Pubblicare il primo commit

```bash
git push -u origin main
```

oppure:

```bash
git push -u origin master
```

L'opzione:

```bash
-u
```

associa il branch locale a quello remoto.

Dopo il primo push sarà sufficiente, per inviare le modifiche committate in locale a GitHub:

```bash
git push
```

per scaricare le eventuali modifiche effettuate su GItHub alla cartella locale linux:

```bash
git pull
```

### Flusso Completo

```bash
mkdir mio-progetto

cd mio-progetto

git init

git add .

git commit -m "Commit iniziale"

git remote add origin https://github.com/utente/mio-progetto.git

git push -u origin main
```

# Modalità 2 - Partire da un Repository GitHub Esistente

Utilizzare questa modalità quando il repository è già presente su GitHub.

## Clonare il repository

Spostarsi o creare la cartella in locale che conterrà il progetto Git e digitare:
```bash
git clone https://github.com/utente/progetto.git
```

Git crea automaticamente:

- la directory del progetto
- il repository locale
- il collegamento al repository remoto

## Entrare nella directory

```bash
cd progetto
```

## Verificare il remote

```bash
git remote -v
```

Output tipico:

```text
origin  https://github.com/utente/progetto.git
```

## Iniziare a lavorare

```bash
git pull (per scaricare eventuali modifiche da GitHub)

# modifiche ai file

git add . (sposta i file nella Staging Area)

git commit -m "Nuova funzionalità" (Sposta i file nel Repository)

git push (Invia ed allinea il repository remoto, GitHub, con le modifiche effettuate in locale=
```

---

# Quando Utilizzare le Due Modalità

## Modalità 1

```text
Nuovo progetto locale
        ↓
git init
        ↓
git remote add origin
        ↓
git push
```

Usata quando si crea un nuovo progetto.

## Modalità 2

```text
Repository GitHub esistente
        ↓
git clone
        ↓
Repository locale
```

Usata quando il progetto esiste già su GitHub.

# Workflow Quotidiano

## Verificare le modifiche

```bash
git status
```

## Aggiungere i file da salvare

Tutti i file:

```bash
git add .
```

Singolo file:

```bash
git add nomefile
```

## Salvare una nuova versione

```bash
git commit -m "Descrizione modifica"
```

Esempio:

```bash
git commit -m "Aggiunta gestione errori"
```

## Inviare le modifiche al repository remoto

```bash
git push
```

## Scaricare le modifiche dal repository remoto

```bash
git pull
```

---

# Visualizzare la Cronologia

```bash
git log --oneline --all --graph
(per vedere lo storico di tutti i branch e del main anche in modo grafico)
```

Esempio:

```text
a34ef12 Aggiunta login
7ab9d44 Correzione bug
4f2e8c1 Commit iniziale
```

---

# Lavorare con i Branch

## Creare un nuovo branch

```bash
git branch feature-login
```

## Passare al branch

```bash
git checkout feature-login
```

oppure:

```bash
git switch feature-login
```

## Creare e passare al branch

```bash
git switch -c feature-login
```
oppure:

```bash
git checkout -b feature-login
```

## Tornare al branch principale

```bash
git switch main
```

oppure:

```bash
git checkout main
```

---

# Unire un Branch

Posizionarsi sul branch principale:

```bash
git switch main
```

Eseguire il merge:

```bash
git merge feature-login
```

---

# Annullare Modifiche Non Salvate

Ripristinare un file facendolo ritornare all'ultimo ***commit***:

Se il file è nella Working Directory:
```bash
git restore nomefile 
```

Se il file è già nella Staging Area:
```bash
git restore --staged file.txt
git restore file.txt
```


---

# Vedere le Differenze

Mostra le differenze dei file presenti nella Working Directory
```bash
git diff
```

Mostra le differenze dei file presenti nella Staging Area
```bash
git diff --staged
```

# Workflow con Branch

```bash
git switch -c feature-login

# modifiche

git add .

git commit -m "Implementazione login"

git push origin feature-login

git switch main

git pull

git merge feature-login

git push

git branch -d feature-login (elimina il branch in locale)

git push origin --delete feature-login (elimina il branch in remoto)
```

# Regola d'Oro

Ogni volta che modifichi del codice:

```text
MODIFICA FILE
      ↓
git status
      ↓
git add .
      ↓
git commit -m "descrizione"
      ↓
git push
```

Questo è il ciclo di lavoro Git utilizzato quotidianamente nella maggior parte dei progetti.
