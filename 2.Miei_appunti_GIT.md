# Comandi e ripensamenti

## Git Commit --amend
```bash
git commit --amend
```
Sovrascrive il commit precedente perdendone le informazioni poco importanti, facendone un merge con quest'ultimo commit.  
(ne fonde 2 in 1) Utilizzato per piccole modifiche, ad esempio per aggiungere il nome alla licenza LICENCE.txt.
Utile perché avere tante righe di commit potrebbe aggiungere un po' di confusione.

## Git Restore
```bash
git restore <file>
git restore --staged <file>
```
Elimina gli ultimi cambiamenti di quel file portandolo alla versione precedente 
(è un undo a livello di file salvato, lo porta al salvataggio e commit precedente)
Il primo comando lavora nella Working Area, il secondo nella Staging Area.

## Git Diff
```bash
git diff "nome file in conflitto di merge"
```
Mostra ad esempio che la stessa riga di un file è stata modificata in entrambi i branch, motivo per il quale non è stato effettuato il merge automatico.  
In questi casi di conflitto si apre il file con nano e lo si modifica secondo quello che umanamente si ritiene corretto.

SPIEGAZIONE DIVERSI TIPI DI MERGE

In Git esistono principalmente 2 tipi di merge:

1. Fast-Forward Merge
2. Three-Way Merge (può generare conflitti)


### Fast-Forward Merge (nessun conflitto)

Si verifica quando il branch main non ha ricevuto nuove modifiche dopo la creazione del branch feature.

Situazione iniziale:

```text
A --- B --- C (main)
             \
              D --- E (feature)
```


Comando:

git merge feature

Risultato:

```text
A --- B --- C --- D --- E  
                  ^  
                  main, feature
```

✅ main non ha modifiche proprie da integrare  
✅ Nessun conflitto  
✅ Nessun commit di merge  
✅ Git sposta semplicemente il puntatore di main


--------------------------------------------------


2. Three-Way Merge con conflitto

Si verifica quando sia main sia feature hanno introdotto modifiche e Git deve combinarle.

Entrambi i branch modificano la stessa riga del file.

Situazione:

```text
      C (feature)
     /
A
     \
      B (main)
```

main:
"Versione MAIN"

feature:
"Versione FEATURE"

Comando:

git merge feature

Git non sa quale modifica scegliere e genera un conflitto:

<<<<<<< HEAD
Versione MAIN
=======
Versione FEATURE
>>>>>>> feature

L'utente deve decidere cosa mantenere e lo decide applicando manualmente le modifiche, aprendo il file con nano e decidendo cosa tenere/modificare/eliminare.

Salva il file senza i commenti GIT ed esegue le operazioni:

git add app.txt
git commit


Risultato finale:

      C (feature)
     /
A --- B -------- M (main)

Dove:
- B = modifica su main
- C = modifica su feature
- M = commit di merge

✅ Commit di merge creato
❌ Conflitto risolto manualmente





# Repository remoto

## Git Remote
```bash
git remote add origin https://github.com/davoliojobGIT/3.VIDEO_CORSO_GIT.git
git remote
(ci dice se c'è collegato alla working directory corrente un Repository Remoto e se si ci ritorna il suo alias,
che solitamente, per consuetudine, si imposta come origin)

git remote -v (da un elenco dei remote repository con anche il link per raggiungerli)
git remote show origin (per mostrare la situazione del repository)
git remote rename origin org (rinomina l'alias del repository remote da origin a org)
git remote rm backup (rimuove un collegamento al repository remoto con alias backup)
```

## Git Push
```bash
git push origin master
```
Per inviare/pusshare i file della working directory GIT corrente sul repository remoto con l'alias origin che sarà collegato al path dato dal comando remote add

## Git Fetch
```bash
git fetch --all
```
Aggiorna le informazioni sui repository remoti senza fare merge.  
Serve, per far avere contezza al DataBase locale di GIT di quali sono gli aggiornamenti presenti sul Server origin verso la working directory locale, con --all scarica da tutti i rami e da tutti i remote che abbiamo configurato.  
Queste differenze ancora non sono state mergiate ma il GIT locale ora sa se e quali modifiche ci sono state sui vari (eventuali) remote repository


## Git Pull
```bash
git pull origin master
```
Scarica e integra le modifiche remote.

<ins>**RAMIFICAZIONI E SVILUPPO PARALLELO**</ins>

\- GIT BRANCH
&nbsp;&nbsp;Permette di lavorare contemporaneamente a più versioni del nostro applicativo  
&nbsp;&nbsp;**git branch carbonara**  
crea un nuovo ramo del repository locale  

&nbsp;&nbsp;**git branch -d nome_branch**  
serve a rimuovere un branch, o meglio la sua etichetta, una volta che lo stesso è stato mergiato con il master
o con un altro branch e quindi nessuna sua modifica andrà persa perché già riunita ad un altro ramo che ora la contiene  

\- GIT CHECKOUT  
&nbsp;&nbsp;**git checkout** ramo (alias)  
ramo sul quale spostare HEAD cioè la nostra Working Directory e quindi ramo con il quale verrnno sincronizzati i cambiamenti
e aggiunti nuovi file  

&nbsp;&nbsp;**git checkout carbonara**  
fa puntare HEAD a carbonara vuol dire che la nostra Working Directory locale è ora associata e si sincronizzerà con il ramo carbonara senza intaccare il
ramo principale master  

  
&nbsp;&nbsp;**git checkout -b salmone**  
effettua tutto in un colpo solo:  
&nbsp;&nbsp;**git branch salmone**  
creare il branch e  
&nbsp;&nbsp;**git checkout salmone**
cioè spostarsici dentro  
<br>
  
<ins>**RIUNIRE I RAMI E RISOLVERE I CONFLITTI**</ins>

\- GIT MERGE  
&nbsp;&nbsp;**git merge nome_branch**  
&nbsp;&nbsp;Fa in modo che il braccio venga mergiato al ramo nel quale ci troviamo, per cui con un checkout ci saremo prima spostati su master.  
I file aggiunti sul branch verranno copiati su master e le modifiche ai file aggiunte.


REGOLA DI MERGE  
\- Le righe eliminate nel branch vengono eliminate anche in master, se nessuno le ha toccate in master;  
\- Le righe modificate nel branch vengono aggiornate in master, se nessuno le ha modificate in master;  
\- Se la stessa area del file è stata modificata in entrambi i rami, Git può generare un conflitto da risolvere manualmente.


\- GIT DIFF  
&nbsp;&nbsp;**git diff "nome file in conflitto di merge"**  
&nbsp;&nbsp;mostra ad esempio che la stessa riga di un file è stata modificata in entrambi i branch, motivo per il quale non è stato effettuato il merge automatico.  

In questi casi di conflitto si apre il file con nano e lo si modifica secondo quello che umanamente si ritiene corretto

\- GIT PUSH

<ins>**RIFONDAZIONE DI UN RAMO**</ins>

\- GIT REBASE  
o rifondazione
serve a far si che un branch possa acquisire le modifice effettuate successivamente alla sua creazione da un ramo master (o altro ramo)
questo semplifica poi la riunione del ramo con master perché potrà effettuare il merge in modalità fast-forward ed automatica

```bash
git rebase master
```

  
Permette a un branch di acquisire le modifiche introdotte successivamente sul ramo principale.  
Va lanciato dentro al ramo che vogliamo acquisisca le modifiche di master
